# Обновления Linux-клиента

AppImage загружается из GitHub Releases репозитория `shiroshy/RuTool`.
Исходники находятся в ветке `linux`, подписанные метаданные канала —
в отдельной ветке `linux-updates-v1`. Канал и ключ выпуска ещё не подготовлены.
Без их настройки клиент сообщает, что автообновление недоступно.

## Настройка сборки

Укажи расположение публичного ключа в переменной `RUTOOL_UPDATE_PUBLIC_KEY`.
Ключ — ECDSA P-256 SPKI DER; он встраивается в приложение.
Закрытый ключ хранится вне репозитория и нужен только для подписи метаданных.
Тестовые ключи для публичного выпуска не подходят.

Команды выполняются из каталога приложения:

```sh
./scripts/build-linux-container.sh "" \
  -DRUTOOL_LINUX_UPDATE_REPOSITORY=shiroshy/RuTool \
  -DRUTOOL_LINUX_UPDATE_CHANNEL_REF=linux-updates-v1 \
  -DRUTOOL_LINUX_UPDATE_PUBLIC_KEY="$RUTOOL_UPDATE_PUBLIC_KEY"
```

Пустой первый аргумент означает сборку с тестами без упаковки.
Для упаковки вместо него нужен новый выходной каталог, как в
[инструкции сборки](../BUILDING-LINUX.md).
Параметры CMake передаются и тестовой, и релизной сборке.
Путь публичного ключа должен быть доступен внутри контейнера;
скрипт сам не подключает внешние каталоги с ключами.

Клиент читает постоянный адрес:

```text
https://raw.githubusercontent.com/shiroshy/RuTool/linux-updates-v1/linux-channel-v1.json
```

Метаданные можно менять без пересборки клиента, пока сохраняются формат
и ключ. AppImage каждого выпуска размещается в Releases того же репозитория.
Канал должен быть доступен без авторизации.

## Формат канала

Внешний JSON содержит `PayloadBase64` и `SignatureBase64`.
Подписываются исходные байты payload алгоритмом ECDSA P-256/SHA-256,
подпись имеет формат P1363.

В payload находятся `FormatVersion: 1`, `Platform: "linux-x86_64"`,
`Repository: "shiroshy/RuTool"`, положительный `Sequence` и массив `Routes`.
Пример маршрута; размер и хеш нужно взять из готового AppImage:

```json
{
  "FromVersion": "0.0.0",
  "BeforeVersion": "2.2.0",
  "Version": "2.2.0",
  "Tag": "v2.2.0",
  "Asset": "RuTool-2.2.0-x86_64.AppImage",
  "Bytes": 50000000,
  "Sha256": "<SHA-256 файла>"
}
```

Маршрут действует от `FromVersion` включительно до `BeforeVersion`
исключительно. Версии состоят из трёх чисел, диапазоны не пересекаются,
а целевая версия не ниже верхней границы. Если маршрута нет, обновление
для текущего клиента недоступно.

При изменении метаданных `Sequence` увеличивается. Клиент сохраняет
наибольшее увиденное значение отдельно для репозитория, ветки и ключа
и отвергает более старые метаданные.

## Подпись

Нужны Python 3.9+ и OpenSSL. Укажи закрытый ключ в переменной
`RUTOOL_UPDATE_PRIVATE_KEY`. Подготовленный payload подписывается так:

```sh
python3 scripts/sign-linux-channel.py channel-payload.json linux-channel-v1.json \
  --key "$RUTOOL_UPDATE_PRIVATE_KEY" \
  --public-key "$RUTOOL_UPDATE_PUBLIC_KEY"
```

Существующие выходные файлы не перезаписываются. Параметр `--public-key`
создаёт публичный ключ при первой подписи; если он уже есть, опусти параметр.
В ветку канала помещается только подписанный JSON. Закрытый ключ не включается
ни в исходники, ни в AppImage.

## Переходные выпуски

Для цепочки `2.1.1 → 2.2.0 → 3.0.0` канал старого клиента сначала указывает
на `2.2.0`. После перезапуска промежуточный клиент снова проверяет канал
и продолжает обновление. Предел — восемь установок за одну цепочку.
Аргумент `--continue-update N` должен сохраняться в будущих версиях
либо заменяться совместимым переходом.

При смене ключа промежуточный выпуск доступен через метаданные, подписанные
старым ключом, но собран с новым публичным ключом и адресом новой ветки канала.
Старая ветка и переходные Releases остаются доступными.
Подписание старой ветки новым ключом лишит старые клиенты обновлений.
Потеря или компрометация закрытого ключа требует отдельного решения.

## Замена и перезапуск

После подтверждения клиент скачивает AppImage и проверяет размер, SHA-256
и заголовок. Перед заменой рядом сохраняется исполняемая предыдущая версия
с суффиксом `.rutool-previous.AppImage`. Подготовленный образ занимает место
текущего, каталоги синхронизируются, затем запускается новая версия.

Если каталог недоступен для записи, клиент предлагает другое место.
Посторонний существующий файл не перезаписывается, исходный образ сохраняется.
Изменение текущего AppImage после запуска требует перезапуска перед обновлением.

Новый процесс запускается с очищенными путями библиотек старого образа
и извлечением без FUSE. Настройки, ключ, журналы и копии игры остаются
вне AppImage. Прерванная загрузка сохраняется для повторной попытки.
Предыдущий образ автоматически не удаляется.

При отказе запуска интерфейс показывает путь для ручного старта.
Автоматического определения сбоя нового GUI и возврата к предыдущей версии нет.
Настоящие переходы между выпусками пока не проверены;
подробности — в [состоянии проверок](LINUX-VALIDATION.md).
