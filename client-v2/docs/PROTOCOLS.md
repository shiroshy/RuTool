# Пакеты и API

Описание форматов и правил клиента RuTool 2.1.1. Серверный код в репозитории
отсутствует: серверные гарантии нельзя установить по одному клиенту.

## Контейнер RUT111

| Поле | Формат |
| --- | --- |
| Заголовок | 32 байта: magic `RUT111\0\0` (8), salt (16), nonce prefix (8) |
| Блок | Длина ciphertext LE32, ciphertext и GCM tag (16 байт) |
| Размер блока | От 1 до 1 048 576 байт |
| Ключ | PBKDF2-HMAC-SHA256, 310 000 итераций, 32 байта |
| Шифрование | AES-256-GCM |
| Nonce | Prefix (8 байт) и LE32 номера блока |
| AAD | Magic и LE32 номера блока |
| Содержимое | ZIP, до 3 ГиБ расшифрованных данных |

Требуется хотя бы один блок. Обрезанные данные, недопустимый размер,
переполнение индекса и ошибка GCM приводят к отказу.
Клиент читает контейнеры, но не генерирует релизные пакеты.

Пароль формата читается из публичной конфигурации приложения.
Он не является секретом и не подтверждает автора пакета.
Проверка структуры контейнера и SHA-256 также не подтверждает подлинность.

## ZIP

Допускаются три набора файлов:

- `ExcelDB.db` и `ExcelDB.db.baretool.json`.
- Те же файлы с `signature.json`.
- Подписанный набор с `Excel.zip`, `resources.assets` и `bundle.json`.

Вложенные пути и дополнительные файлы не принимаются. Проверяются заголовки,
CRC, размеры, границы записей и отсутствие пересечений. Дубликаты имён,
символические ссылки и неподдерживаемые флаги отвергаются.
Разрешены методы ZIP 0 и 8. Лимит одного файла — 1 ГиБ, суммы — 3 ГиБ,
центрального каталога — 64 КиБ.

После распаковки проверяются manifest версии 1, хеш переведённой базы
и состав bundle. Проверка повторяется перед установкой.

## Подписи и официальность

Подпись — ECDSA P-256/SHA-256 в формате IEEE P1363: `r || s`, 64 байта.
Публичный ключ — канонический DER SPKI, 91 байт.
DER-подпись ECDSA не взаимозаменяема с P1363.
Канонические сообщения требуют точного порядка полей, кодировки,
переводов строк и little-endian представления чисел.

Официальность пакета подтверждается через `api/verify`.
Скачанный неподтверждённый пакет отвергается. Для локального пакета
есть отдельный сценарий с предупреждением и подтверждением.
Ошибка сервера не считается успешной проверкой.

Официальность пакета и подтверждение исходного игрового файла — разные
признаки. От второго зависит сохранение постоянной копии оригинала.
Ни один из них нельзя получить из одного лишь хеша.

## HTTP API

Основной адрес — `https://bluehalo.site/`.

| Запрос | Назначение |
| --- | --- |
| `/healthz` | Доступность сервиса |
| `/api/installer/content` | Тексты и Credits |
| `api/verify` | Проверка подписи и аттестации |
| `api/installer/releases/latest` | Последний публичный перевод |
| `api/installer/premium/check` | Код доступа и срок Premium |
| `api/installer/premium/releases` | Premium-каталог |
| `api/installer/installations` | Счётчик и регистрация установки |
| `api/installer/application/v2/latest`, `candidate` | Метаданные Windows-обновления |

JSON-клиент работает в рабочем потоке: запрос до 16 КиБ, ответ до 1 МиБ,
таймаут передачи 15 секунд, общий — 20 секунд. Список адресов ограничен.
Асинхронные ответы health, content и Windows-анонса ограничены
4 КиБ, 384 КиБ и 1 МиБ соответственно.

Имена полей принимаются в PascalCase и с первой строчной буквой.
Произвольное изменение регистра не допускается.
Windows-анонс может читаться при проверке связи, но не используется
для Linux-обновления.

Отчёты отправляются отдельным multipart-запросом. Linux добавляет `[Linux]`
и перевод строки в начало текста. Из лимита 400 Unicode-кодовых точек
пометка занимает восемь; для текста остаётся 392.
Вложения проверяются по правилам клиента, но не очищаются от личных данных.

## Каталог и загрузки

Публичный каталог содержит ReleaseId, PackageVersion, MinimumInstallerVersion,
OriginalDatabaseSha256, PackageSha256, PackageBytes, Sequence, PublishedAtUtc,
PackageUrl и PackageAttestation. Клиент проверяет совместимость версии,
размер до 2 ГиБ, хеши и отсутствие отката ниже сохранённого Sequence.

Разрешены публичные пакеты из GitHub Releases репозитория `shiroshy/rut_files`
с именем `translation.rut` и пакеты сервиса из `/installer/packages/`.
Для GitHub требуются положительный Sequence и согласованная аттестация.

Загрузчик допускает только HTTPS-хосты bluehalo.site, github.com,
release-assets.githubusercontent.com и objects.githubusercontent.com.
Каждый адрес перенаправления проверяется заново.

Незавершённые загрузки сохраняются с суффиксом `.partial`.
Для докачки проверяются Content-Range, размер и SHA-256.
Ответ HTTP 200 вместо диапазона перезапускает загрузку с начала.
Повреждённые данные удаляются, прерванные сетевые загрузки могут сохраняться.

Premium-пакеты загружаются только с bluehalo.site по адресам
`api/installer/premium/packages/<id>` и `api/installer/premium/addons/loading-screens`.
ID — 32 шестнадцатеричных символа либо `main`.
Код передаётся как Bearer; перенаправления и отправка кода обычному URL
запрещены. HTTP 401/403 означает отказ в доступе.

## Дополнение RUTD1

Заголовок — `RUTD1\0`, затем команды copy/literal с little-endian словами.
Вход и результат ограничены 64 МиБ, длина результата совпадает с оригиналом.
Допустимые размер и хеши игрового bundle закреплены в установщике.
Дополнение хранит собственную резервную копию; восстановление основного
перевода не восстанавливает его.

## Локальные данные Linux

Формат защиты — `RULOC1` (6 байт), nonce (12), tag (16), ciphertext.
AES-256-GCM использует AAD из magic и переданного контекста.
Для журнала контекст включает полный путь целевой базы.

Случайный 32-байтовый ключ хранится отдельно от AppImage.
Перед использованием проверяются владелец, права, размер, сохранение на диск
и чтение ключа. Потеря ключа блокирует расшифровку.
Процессы того же пользователя потенциально могут прочитать его.
Формат несовместим с Windows DPAPI.

Изменение контекста, пути или формата требует решения о миграции.
Идентификатор установки на основе machine-id и uid не является секретом
или средством авторизации.

## Обновление клиента

Linux использует отдельный [подписанный канал](LINUX-UPDATES.md).
Windows-контракт требует EXE/DLL и не применяется к AppImage.
Windows-helper получает локальный план от GUI и самостоятельно не повторяет
проверку подписи метаданных.

Структура пакета, целостность, подпись, серверное подтверждение и Premium-доступ
проверяются отдельно. Сетевые тесты используют искусственные ответы;
рабочий сервер и действующие коды для них не нужны.
